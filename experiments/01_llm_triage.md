# 01. LLM 영향 판별 실험

- 날짜: 2026-11-03
- 스크립트: `src/llm_triage.py`
- 모델: `gpt-5-mini` (OpenAI Responses API)

## 목적

스캔 결과(취약점 목록)와 코드 사용 위치를 LLM에 주면, 취약점이 서비스에 실제로 영향을 주는지 판단하고 쓸 만한 조치안을 내는지 확인한다. 어디서 틀리는지도 함께 본다.

## 입력

- 대상 서비스: 팀 프로젝트 웹 저장소 백엔드 (FastAPI)
- 취약점: 2026-10-28 Syft → Trivy 스캔 결과에서 3개 패키지만 추출 (`data/inputs/vulns.json`)
- 코드 사용 위치: grep으로 import·호출 위치와 앞뒤 몇 줄 추출 (`data/inputs/usage.txt`)

| 패키지      | 설치 버전 | 취약점 수 | 코드 사용                         | 특징                                        |
| ----------- | --------- | --------- | --------------------------------- | ------------------------------------------- |
| python-jose | 3.3.0     | 3         | 인증 모듈에서 JWT encode/decode   | CRITICAL 1건은 수정 버전 없음               |
| pillow      | 12.1.1    | 59        | 업로드 이미지 처리에서 Image.open | 수정 버전 12.2.0 / 12.3.0 / 13.0.0 (메이저) |
| anyio       | 4.13.0    | 2         | 직접 import 없음                  | FastAPI·Starlette가 내부에서 사용           |

## 조건

- A: 취약점 목록만 입력
- B: 취약점 목록 + 코드 검색 결과(검색 범위·패턴 설명 포함) 입력

출력은 JSON 형식으로 강제 (`impact`, `reason`, `evidence`, `action`, `recommended_version`, `action_detail`, `cited_ids`).
`impact`는 "영향 있음 / 낮음 / 해당 없음 / 확인 필요" 중 하나.

## 결과

| 패키지      | A                          | B                          | 기대 판단           |
| ----------- | -------------------------- | -------------------------- | ------------------- |
| python-jose | 확인 필요 / upgrade 3.4.0  | 영향 있음 / upgrade 3.4.0  | 영향 있음 / replace |
| pillow      | 확인 필요 / upgrade 13.0.0 | 영향 있음 / upgrade 13.0.0 | 영향 있음           |
| anyio       | 확인 필요 / upgrade 4.14.2 | 해당 없음 / none           | 낮음                |

## 검증

- 출력 전체(설명 문장 포함)에서 CVE/GHSA ID를 추출해 입력 ID와 비교 → **입력에 없던 ID 0개**
- 추천 버전을 `pip index versions`로 확인 → anyio 4.14.2, pillow 13.0.0, python-jose 3.4.0 **모두 PyPI에 존재**, Trivy 수정 버전과 일치
- python-jose PyPI 최신 버전은 3.5.0, 수정 버전이 없는 CRITICAL(CVE-2026-85394)은 제목에 "through 3.5.0" → **최신 버전으로 올려도 해결되지 않음**

## 발견

1. **코드 맥락이 판단을 바꾼다.** A에서는 세 패키지 모두 "확인 필요"였지만, B에서는 영향 있음/해당 없음으로 나뉘었다. pillow는 외부 입력(`image_bytes`)이 `Image.open`으로 바로 들어가는 경로를 근거로 들고 코드 줄 번호까지 정확히 인용했다.
2. **환각은 없었다.** 취약점 번호와 추천 버전을 지어내지 않았다.
3. **설명과 구조화 필드가 어긋난다.** python-jose의 `action_detail`에는 "수정 버전이 없어 업그레이드만으로 해결되지 않을 수 있다, 교체 검토"라고 썼지만, `action`과 `recommended_version`은 `upgrade` / `3.4.0`이었다. 시스템이 구조화 필드만 보고 자동 처리하면 CRITICAL이 남은 채 완료 처리된다.
4. **직접 사용과 런타임 사용을 구분하지 못한다.** anyio는 직접 import가 없다는 이유로 "해당 없음"이 됐지만, 실제로는 프레임워크가 실행 중에 쓴다. 다만 프롬프트의 검색 범위 설명("나오지 않으면 직접 import하지 않는다는 뜻")이 이 해석을 유도했을 수 있다.

## 시사점 (기획안 설계와 연결)

- 정적 분석 결과를 LLM 입력에 함께 넣어야 한다 (발견 1)
- 규칙 기반 사후 검증이 필요하다: `fixed`가 null인 취약점이 하나라도 있으면 `upgrade`만으로 완료 처리하지 않는다 (발견 3)
- import 검색만으로는 부족하고 의존성 그래프(전이 의존성)를 함께 봐야 한다. 근거가 부족하면 "해당 없음" 대신 보수적으로 판단해야 한다 (발견 4)
